# Phase 0 Research: Super Admin RBAC Login & Console Access

All decisions below were resolved interactively with the user during Specify/Clarify (see spec.md's Clarifications-equivalent resolution), or are direct, low-risk implementation consequences of those resolutions. No `NEEDS CLARIFICATION` markers remain in the Technical Context.

## R1: Physical shape of the "Clinic Portal"

**Decision**: Reuse the existing staff login screen (`/staff/login` route, `StaffLoginForm`) and endpoint (`POST /api/v1/staff/login`, `StaffAuthController`) as the Clinic Portal, rather than creating a new URL/route/endpoint. Only the UI copy changes (heading/description now addresses "Clinic sign in" covering staff and Super Admin); the login field shape (`identifier` + `password`) is already exactly what a combined form needs, since `003-staff-login-password-or-code`/`006` already made `identifier` accept either an email or a staff code — a Super Admin's configured username slots in as a third possible value with zero UI change.

**Rationale**: The spec's Clinic Portal requirement is behavioral (one shared screen/endpoint that resolves to either identity), not a request for a new URL. Reusing the existing route/endpoint is the smallest change that satisfies FR-001/FR-003, avoids introducing a second, parallel "identical-looking" login mechanism, and keeps every existing staff-login test (`StaffLoginForm.test.tsx`, `006`'s contract tests) valid for the staff path with no changes beyond the additive `role` field (R3).

**Alternatives considered**: A new `/clinic-portal/login` route and endpoint — rejected as pure churn; it would require redirecting or duplicating the already-converged, already-tested staff login path for no behavioral benefit (Constitution II, Simplicity/YAGNI).

## R2: Where the Super-Admin-vs-staff resolution happens

**Decision**: `StaffAuthController.login` tries the Super Admin credential check first (cheap: one in-memory `UserDetails` comparison, no DB round-trip), then falls through to the existing `AccountRepository` email-or-staff-code lookup unchanged. Both failure paths converge on the same `InvalidCredentialsException` (unchanged), so FR-004 (one generic error) holds structurally, not just by convention — it's the same exception object every non-match path already threw before this feature.

The Super Admin check itself is **not** two raw beans (`superAdminUserDetailsService`, `SuperAdminJwtService`) injected directly into `StaffAuthController` — that would have `com.cms.identity.account` reach into `com.cms.identity.admin`'s internals across the exact "entirely separate identity mechanisms" boundary this codebase's own design repeatedly documents (spec.md's Codebase Context; `SuperAdminSecurityConfig`'s own Javadoc), violating Constitution III's "each module MUST expose a clear contract." Instead, `com.cms.identity.admin` exposes exactly one new contract method for this purpose — `SuperAdminAuthenticationService.authenticate(String identifier, String password): Optional<String>` (returns an issued Super Admin JWT on a match, empty otherwise), internally composing the existing `superAdminUserDetailsService` bean and the new `SuperAdminJwtService` (R3). `StaffAuthController` depends on only this one method, the same way it already depends on `AccountRepository`/`PasswordEncoder`/`StaffJwtService` as its own module's concerns — a normal Spring service dependency, not a cross-module bean reach-through.

**Rationale**: Matches this codebase's own established "resolve identity by trying storage backends in a defined order" idiom (e.g. `AccountRepository.findByEmail(...).or(() -> findByStaffCode(...))` already does exactly this for the two staff identifiers). Extending that `.or(...)` chain conceptually with a Super-Admin-credential check first keeps the whole resolution in one place (FR-003), and "try the cheap, non-DB check first" is a reasonable, low-risk default given there is exactly one Super Admin credential to compare against (Assumption in spec.md). Routing that check through one exposed `SuperAdminAuthenticationService` method (rather than two raw beans) keeps `com.cms.identity.admin`'s internals — its `UserDetailsService`, its JWT signing details — encapsulated, satisfying Constitution III without adding a new module or an event (this is a synchronous, request-scoped concern, not the kind of asynchronous cross-module effect Principle III's event-driven requirement targets).

**Alternatives considered**: A separate `/api/v1/admin/login` endpoint the frontend calls first, falling back to `/api/v1/staff/login` on failure — rejected because it would require two round-trips on every staff login (bad UX, and leaks information: a caller could distinguish "not super admin" from "not staff" by timing/response of two separate calls, weakening FR-004's information-hiding intent) and duplicates validation logic Spring MVC would otherwise unify in one request.

## R3: Super Admin session mechanism — new JWT, replacing Basic Auth

**Decision** (resolved with user, Q1): Introduce `SuperAdminJwtService` (mirrors `StaffJwtService`/`patient.account.JwtService` exactly): its own HMAC secret (`admin.super-admin.jwt.secret`, new config key, same "dev-only default, override via env var" pattern as `STAFF_JWT_SECRET`/`PATIENT_JWT_SECRET`), audience claim `SUPER_ADMIN`, subject = the configured Super Admin username (there being no DB row/UUID to use instead), same 12-hour TTL as the staff token (spec Assumption — no stated requirement for a shorter session). `StaffAuthController.login`, on a Super Admin match, calls this service instead of `StaffJwtService` and returns the token in the same `StaffLoginResponse` shape, with a new `role` field (`"SUPER_ADMIN"` vs `"STAFF"`, R4) telling the frontend which one it got.

`SuperAdminSecurityConfig.adminFilterChain` is changed from `.httpBasic(withDefaults())` + `.userDetailsService(...)` to `.addFilterBefore(new SuperAdminJwtAuthenticationFilter(superAdminJwtService), UsernamePasswordAuthenticationFilter.class)` + `.exceptionHandling(ex -> ex.authenticationEntryPoint(superAdminAuthenticationEntryPoint))`, mirroring `com.cms.identity.account.SecurityConfig`'s staff chain structure exactly (`StaffJwtAuthenticationFilter`, `StaffAuthenticationEntryPoint`, both deliberately-not-`@Component` / `@Component` respectively for the same reasons already documented on those classes). `/api/v1/admin/**` still requires `.anyRequest().authenticated()` — only the credential-verification mechanism changes, not the authorization shape.

The existing `superAdminUserDetailsService` bean (in-memory `UserDetailsService`, random-password-if-unconfigured safety behavior) is kept as-is and reused inside the new `SuperAdminAuthenticationService` (R2) — it is simply no longer wired into Spring Security's `httpBasic()` mechanism, only consulted at login time, and never exposed outside `com.cms.identity.admin` directly (R2's contract boundary). This preserves FR's "unconfigured Super Admin is unreachable, not a known default" safety guarantee unchanged, just via a login failure instead of a Basic Auth failure.

**Rationale**: User-selected option (Q1); also structurally consistent — every other identity in this system (staff, patient) already authenticates via a JWT with its own audience/secret pair, and `SecurityConfig.currentAccountId`/`patient.account.SecurityConfig.currentPatientAccountId` already establish the "static helper extracts the typed principal `UsernamePasswordAuthenticationToken` set by our own filter" pattern this feature's `SuperAdminSecurityConfig.currentSuperAdmin`-equivalent helper will follow.

**Alternatives considered**: Keeping Basic Auth as the actual backend mechanism and only adding a client-side "remembered credential" session (Q1's Option A) — rejected by the user; also would have left a raw password sitting in browser storage for the session's duration, a weaker posture than a scoped, expiring JWT.

## R4: Response/DTO shape

**Decision**: `StaffLoginResponse` (record) gains one new field: `role` (`String`, values `"STAFF"` or `"SUPER_ADMIN"`) — additive, so any existing consumer that ignores it is unaffected. For a Super Admin match, `accountId` is `null` (no DB row exists) and `email` holds the Super Admin's configured username (repurposing the existing field rather than adding a second identity-label field, since no consumer treats it as a validated email address — it is only ever displayed/stored, never parsed). `StaffLoginRequest` is unchanged (`identifier` + `password` already fits both cases, R1).

**Rationale**: Smallest possible contract change; keeps one response type for the one (now dual-purpose) endpoint, consistent with this codebase's preference for additive, non-breaking DTO evolution (e.g. how `035-prescription-and-items-creation` extended rather than forked its sibling's shape).

**Alternatives considered**: A discriminated-union response (`ClinicPortalLoginResponse` wrapping either a `StaffLoginResult` or `SuperAdminLoginResult`) — rejected as more ceremony than the two-field difference (`accountId`, `role`) justifies (Constitution II).

## R5: Frontend redirect decision point (FR-011)

**Decision**: A small, pure, independently-testable function (e.g. `decideClinicPortalDestination(role: 'STAFF' | 'SUPER_ADMIN'): string`) in the `staff-login` feature folder, returning `/super-admin-console` or `/staff`. `StaffLoginPage`'s `onSuccess` handler calls it instead of hardcoding `navigate('/staff', ...)`. The Patient Portal's own, separate, already-converged redirect (`/patient`) is untouched (FR-002/FR-007) and does not call this function — there is only one real "which of several destinations" branch in this feature (Super Admin vs staff), so the "shared decision point" is this one function, not a cross-portal dispatcher.

**Rationale**: Satisfies FR-011 literally (one shared decision point, not duplicated inline branching) while staying proportionate — a full "role router" abstraction spanning all three portals would be speculative generality the current requirement doesn't call for (Constitution II).

## R6: Super Admin session storage and route guard

**Decision**: New `frontend/src/features/super-admin/token.ts` (mirrors `staff-login/token.ts`/`patient-account/token.ts` exactly: `sessionStorage`, key `cms.superAdminToken`, `{ token, username }` shape, `loadSuperAdminSession`/`storeSuperAdminSession`). New `RequireSuperAdminSession` guard in `routes/guards.tsx` (mirrors `RequireStaffSession`/`RequirePatientSession` exactly), redirecting to `/staff/login` (the Clinic Portal, per spec Assumption "kick back to the Clinic Portal login screen specifically") when no session is present.

**Rationale**: Direct precedent-following — this is the third instance of the identical "typed sessionStorage session + route guard" pattern in this codebase; no new design needed.

## R7: Existing `/admin/*` screens move under the new guarded `/super-admin-console` prefix and switch from Basic Auth to the stored JWT

**Decision**: `App.tsx`'s current unguarded `<Route path="/admin" element={<AdminShell />}>` block is replaced by `<Route path="/super-admin-console" element={<RequireSuperAdminSession />}><Route element={<AdminShell />}>...</Route></Route>`, matching the `RequireStaffSession`/`StaffShell` nesting shape already used for staff routes. `AdminShell`'s internal nav links (`/admin/clinics` etc.) are updated to the new prefix. The three existing admin screens (`PendingClinicsList`, `PendingDoctorsList`, `TriggerSessionGeneration`) and their three `api.ts` files each currently duplicate an identical `AdminCredentials { username, password }` + `Basic ${btoa(...)}` helper and a local login form embedded in the component itself — all three are updated to accept a bearer token (from the new `super-admin/token.ts`) instead of `AdminCredentials`, and their embedded login forms are deleted (login now happens once, at the Clinic Portal, per FR-001).

**Rationale**: FR-012 removes Basic Auth as a valid way to reach `/api/v1/admin/**` at all — these three screens' existing per-call Basic Auth is the only caller of that mechanism, so updating them is a direct, unavoidable consequence of R3, not scope creep (spec.md's own Assumption already calls this out as in-scope). Moving the routes under `/super-admin-console` directly satisfies FR-008/SC-002 (today's `/admin` route has no guard at all — leaving it live and unguarded while adding a new guarded alias elsewhere would leave the actual security hole from the source request's premise open).

**Alternatives considered**: Keeping `/admin/*` as a second, unguarded path alongside a new guarded `/super-admin-console` — rejected outright; it would satisfy the letter of FR-005/FR-008 while leaving the exact vulnerability (an unguarded console route) the feature exists to close.

## R8: Consolidating the three duplicated `AdminCredentials`/`authHeader` helpers

**Decision**: While updating the three `api.ts` files (R7), replace each file's own local `AdminCredentials`/`authHeader`/Basic-Auth block with a single shared `Authorization: Bearer <token>` header, built inline (`` `Bearer ${token}` `` — one line, no helper function needed now that there's no encoding step) rather than introducing a new shared module purely for that one-liner.

**Rationale**: Removes the Basic-Auth-specific duplication (`btoa` encoding) that no longer applies, without inventing a new cross-feature "admin API client" abstraction the current requirement doesn't call for (Constitution II) — each `api.ts` file keeps its existing per-feature scope, just swapping its auth-header construction.

## R9: Regression surface — every existing `/api/v1/admin/**` test uses Basic Auth

**Discovery**: `AbstractAdminIntegrationTest` (the shared base class for ~15+ existing integration test classes across `002`, `005`/`006`, `007`/`008`, `011`, `034` — everything that ever authenticated as Super Admin in a test) defines one `superAdminAuthHeader()` helper that every subclass calls to build its `Authorization` header. Replacing Basic Auth with bearer JWT (R3) would otherwise break all of them simultaneously.

**Decision**: Change only `AbstractAdminIntegrationTest.superAdminAuthHeader()`'s internal implementation — from building a `Basic ...` header to issuing a real Super Admin JWT (via a `SuperAdminJwtService` bean, autowired into the base class the same way `PasswordEncoder` already is) and returning `Bearer <token>`. Every existing subclass keeps calling `superAdminAuthHeader()` exactly as before, unaware anything changed. `AdminAuthorizationTest`'s two "valid staff Account credentials are still rejected" tests are updated to build a staff JWT (via `StaffJwtService`, already a Spring bean) instead of a staff Basic Auth header, since Basic Auth of any kind is no longer meaningful to send. One new test is added there confirming a correct-credential Basic Auth header is now rejected outright (FR-012).

**Rationale**: Contains the entire backend test-regression surface to one helper-method change plus one existing test file's two assertions, instead of a 15+-file mechanical edit — the same "change the one seam every caller already goes through" principle already applied in R2/R8.
