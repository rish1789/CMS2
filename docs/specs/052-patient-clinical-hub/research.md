# Research: Patient Context & Clinical History Hub

## Decision 1: A navigation hub, not a content-aggregation hub

**Decision**: The Consultations/Prescriptions/External Records sections list the patient's bookings as clickable rows linking into the existing, unmodified `bookings/:id/consultation-note` / `.../prescription` / `.../external-record` pages. The hub itself never fetches or inlines a note/prescription/record's own content.

**Rationale**: Verified via a full codebase investigation (not assumed) that all three record types are exclusively `bookingId`-scoped — no patient-level list endpoint exists for any of them, frontend or backend (`GET .../bookings/{bookingId}/consultation-notes` returns one note for one booking; same shape for prescriptions/external-record-references). Each is gated by `TreatingDoctorAuthorizationService.requireTreatingDoctor`, called individually per booking inside `ConsultationNoteService`/`PrescriptionService`/`ExternalRecordReferenceService`. A content-aggregation hub (fetch-and-inline every note/prescription/record for a patient's bookings) would need to either (a) fan out N+1 (×3 record types) HTTP calls per hub load, or (b) stand up 3 new aggregate backend endpoints that internally re-run the exact same per-booking authorization check in a loop — a real risk of the check drifting out of sync with the original over time, which spec.md FR-006 explicitly forbids ("does not relax, duplicate, or bypass"). Linking into the existing pages instead means the existing authorization runs completely unmodified, on the existing code path, with zero new authorization code anywhere — the strongest possible guarantee against regression, and the same "condensed list linking into an existing detail page" pattern 048's dashboard ("Today's sessions" → Day Sheet) already established as this codebase's convention for exactly this kind of aggregation.

**Alternatives considered**: 3 new aggregate endpoints returning full note/prescription/record content, each re-applying `TreatingDoctorAuthorizationService` per row — rejected per FR-006 and Principle II (the query complexity and duplicated-authorization-surface aren't justified when the existing per-booking pages already do this correctly); N+1 client-side fan-out to *check existence* before rendering a row (so unavailable rows could be greyed out) — rejected as unnecessary complexity for a first pass (Principle II); the destination pages already handle "no note yet" (create) vs "note exists" (view) without the hub needing to know in advance.

## Decision 2: One new backend query — a clinic+patient-scoped booking list

**Decision**: Add `BookingRepository.findByPatient_IdOrderBySlot_Session_SessionDateDesc(UUID patientId, Pageable pageable)` — a derived Spring Data query method, mirroring the exact naming/shape convention of the existing `findByPatient_PatientAccount_IdOrderByCreatedAtDesc` (021's patient-self-service "my bookings" query). Exposed via a new `PatientBookingHistoryController` (`GET /api/v1/clinics/{clinicId}/patients/{patientId}/bookings`) in `com.cms.patient.record.api`, reusing `PatientDetailController`'s own established clinic-ownership check (`patientRepository.findById(patientId).filter(p -> p.getClinic().getId().equals(clinicId))`) before querying bookings — this is what makes the query clinic-scoped: a `Patient` row belongs to exactly one clinic (`Patient.clinic`, `@ManyToOne(optional = false)`), so once the caller is confirmed to be staffed at `clinicId` and `patientId` is confirmed to belong to `clinicId`, `findByPatient_Id(patientId)` cannot return another clinic's data by construction.

**Rationale**: Verified this capability doesn't exist anywhere today (frontend or backend) — the closest existing query, `findByPatient_PatientAccount_IdOrderByCreatedAtDesc`, is scoped by `PatientAccount` (the cross-clinic login identity), used only by the patient-self-service `GET /api/v1/patients/bookings` endpoint, and deliberately spans every clinic — the opposite of what a staff-side, clinic-scoped hub needs (spec.md FR-003). A derived query method (no custom JPQL needed) is the minimal addition, matching this repository's own established pattern for exactly this shape of lookup.

**Alternatives considered**: Reusing/extending `SessionDaySheetController`'s day-sheet endpoint with a patient filter — rejected, that endpoint is session-scoped (one day's sessions for a clinic), structurally the wrong shape for "one patient's full history," and would conflate two different call sites' concerns; querying via `PatientAccount` and filtering client-side to the current clinic — rejected, `Booking.patient` (not `Booking.patient.patientAccount`) is the correct clinic-scoped relationship already, and client-side filtering of a cross-clinic dataset is exactly the "let backend leak cross-clinic data, hope frontend hides it" anti-pattern the constitution's multi-tenancy rule exists to prevent.

## Decision 3: Expose `anonymizedAt` by extending the existing shared DTO

**Decision**: Add `anonymizedAt: Instant | null` to `PatientSearchResultResponse` (both its Java record and `.from(Patient)` factory), which already backs 3 existing call sites (`ClinicPatientSearchController`'s list, `PatientDetailController`'s single-patient lookup, and — after this feature — the hub's Overview section). No new DTO, no new endpoint.

**Rationale**: Verified the frontend currently has zero way to detect "this patient is already anonymized" outside the instant right after the anonymize action itself succeeds (grep-confirmed: `anonymizedAt` appears in exactly one frontend file, the anonymize-response type). `Patient.anonymizedAt` is already a persisted column (033) — this is a response-shape gap, not a data gap. Extending the already-shared DTO means `PatientSearch.tsx`'s existing result list and the hub's Overview both get this for free from the same backend change.

**Alternatives considered**: A separate "hub overview" DTO distinct from `PatientSearchResultResponse` — rejected, would duplicate 3 fields for zero benefit (Principle II) when the existing DTO already serves every call site that needs identity info.

## Decision 4: Tab/section navigation — client-side state, not nested routes

**Decision**: `PatientHubPage`'s 5 sections (Overview/Bookings/Consultations/Prescriptions/External Records) are plain client-side tab state (`useState`), not separate nested routes.

**Rationale**: None of the 5 sections needs its own deep-linkable URL for this first pass (no spec requirement names one), and every other tabbed UI already in this codebase (e.g. `PendingClinicsList`/`PendingDoctorsList`'s Pending/Verified/Rejected tabs) already uses the identical plain-state pattern rather than nested routes — matching established convention over inventing a new one (Principle II).

**Alternatives considered**: Nested routes per tab (`/patients/:patientId/bookings`, etc.) — rejected as unrequested complexity; no acceptance scenario needs a shareable link to one specific tab.
