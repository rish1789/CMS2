The product owner found the sidebar/forms/fields placed 'irrationally,' wasting space and looking sloppy, and page headings/subheadings reading as generic ('guide for a 3 year child') rather than meaningful. ## Clarifications

### Session 2026-09-16

- Q: Which specific screen(s) does the wasted-space / irrational sidebar-field-form placement problem apply to? → A: It's structural, not screen-specific — `StaffShell.tsx` (`mx-auto max-w-5xl`) centers the entire staff console including the sidebar, `ClinicShell.tsx` nests the sidebar inside that constrained column via `flex gap-6`, and individual forms (e.g. `OnboardStaffForm.tsx`'s own `mx-auto max-w-xl`) add a third nested centered layer on top — three nested centered boxes shrinking toward the middle, present on every screen that inherits `StaffShell`/`ClinicShell`. The product owner pointed to a downloaded reference (`orbit-1.0.0.zip`, the "Orbit" MIT-licensed React/Tailwind admin dashboard template by ThemeWagon) whose `Layout.tsx`/`Sidebar.tsx` uses the opposite pattern: a `fixed left-0 top-0 h-screen` sidebar docked to the actual viewport edge (collapsible 256px ↔ 72px), with content taking the full remaining width via a `margin-left` offset — no centering, no nesting.
- Q: Should the layout fix apply Orbit's structural pattern using CMS2's existing palette, or also adopt more of Orbit's own visual look (dark surfaces, glow effects, animation)? → A: Structure only. Adopt the edge-docked fixed sidebar / full-width content mechanics; keep CMS2's existing indigo/gray/cobalt palette and `PRODUCT.md`'s restrained clinical tone. Orbit's own dark, neon-glow "AI SaaS" skin is explicitly the kind of decorative, generic-SaaS look `PRODUCT.md`'s Design Principles say this product should avoid.
- Q: Should the structural layout fix apply to the shared shell (fixing every staff-console screen at once) or stay scoped to just the two screens originally being looked at? → A: Fix the shared shell — `StaffShell.tsx` and `ClinicShell.tsx` — so every screen that inherits it (not only `ClinicToolsDashboard.tsx` and `OnboardStaffForm.tsx`) is corrected by the same structural change. Scope is the staff console only (screens under `StaffShell`/`ClinicShell`); `PatientShell`/`AdminShell` and the screens under them are not part of this pass unless separately named.
- Q: Which specific heading/subheading text does the product owner consider to have "no meaning" or to read as "a guide for a 3 year old"? → A: The public landing/role-selection page, `frontend/src/routes/HomePage.tsx` (reached at `/`, before any login) — specifically: the title "One account, every clinic."; the subheading "Book appointments as a patient, run day-to-day operations as clinic staff, or manage verification as a Super Admin."; the "Patients" card body "Book appointments, join queues and waitlists, and manage your visits."; the "Clinic staff" card body "Manage schedules, bookings, walk-ins, and the day-to-day of your clinic."; the "Running a clinic?" card ("Register your clinic and admin account."); and the "Super Admin? Open the admin console" line. No other screen's copy has been raised as a problem in this session.

### Session 2026-09-16 (continued — mid-implementation pivot)

- Q: While `HomePage.tsx`'s copy fix (FR-009, original scope) was awaiting sign-off, the product owner instead directed a full rebuild of `HomePage.tsx` from a prepared external reference design (a published Claude Artifact, saved locally as `design/landing-page-reference.html`), with explicit new requirements: patient-booking content dominates the hero; clinic-side access becomes a single, low-emphasis "Clinic login" link (header + footer only); no separate/public Super Admin link; Super Admin authentication and clinic registration (`/register`) both move behind that one "Clinic login" entry point, role-routed after sign-in, instead of being separate top-level links; the reference's placeholder brand ("Carepoint"), copy, and anchors (`#login` etc.) are replaced with this project's real name/copy/routes; this project's own existing design tokens (`index.css`'s `@theme`, Figtree font) are used instead of the reference's own palette/serif font, since a system already exists. → A: This supersedes and significantly expands FR-006's original "no new functionality, new routes... only layout/spacing/placement and copy changes" boundary and FR-009's original "6 confirmed text elements" scope — both are updated below (FR-006 amended, FR-009 superseded, FR-010/FR-011 added) rather than silently ignored, per Constitution Governance's "no silent deviation." No new backend route or endpoint is added — `/staff/login`'s existing role-based post-login redirect (`decideClinicPortalDestination`, 040-super-admin-rbac-login) already sends Super Admins to `/super-admin-console` and staff to `/staff`, so "Super Admin auth lives behind Clinic login" required zero routing-logic change, only removing the homepage's separate link to it and adding a link to `/register` on the Clinic login page itself.

### Session 2026-09-16 (continued — second mid-implementation pivot)

- Q: Immediately after the `HomePage.tsx` rebuild, the product owner directed the same treatment for `/patient/login`: rebuild it from a second prepared reference (`design/patient-login-reference.html`) — branded header/footer matching the new landing page, a centered card ("Welcome back." heading, email/password fields, inline "Forgot password?" next to the Password label, full-width primary button, a quiet divider + "Create an account" line), reusing the same tokens, wired to real auth. → A: Extends FR-009a's "rebuild from reference, our tokens/copy/routes, not the reference's brand/palette/font" pattern to `LoginForm.tsx`/`PatientLoginPage.tsx` (FR-012, added below). One real gap surfaced: no password-reset capability exists anywhere in this system (frontend or backend) — building one (reset tokens, email delivery) is a new feature, not a restyle, and collides with the constitution's explicit "no live notification delivery integration" out-of-scope boundary until a documented product decision changes it. Resolved without asking a fourth clarifying round (the answer follows directly from already-ratified constitution text, not a new judgment call): "Forgot password?" is wired to an honest in-app notice (a toast: "Password reset isn't available yet — contact your clinic for help.") rather than either a dead placeholder link or a fabricated reset flow. A real password-reset feature, if wanted, is a separate, new backlog feature requiring its own spec.

### Session 2026-09-16 (continued — third mid-implementation pivot)

- Q: The product owner then directed the same treatment for `/patient` (`PatientDashboard.tsx`), from a third prepared reference (`design/patient-dashboard-reference.html`): branded header matching the login/landing pages but with an account menu (avatar/email/sign-out) instead of a "Clinic login" link, a personalized "Welcome back, {firstName}." heading, a highlighted "next visit" strip shown only when a real upcoming booking exists, and three action cards (Find a doctor, My bookings, My clinics). → A: Extends the same "rebuild from reference, our tokens, real data/routes" pattern (FR-013, added below). Two things already existed and needed no new building: (1) the "only when a booking exists" conditional next-visit logic was already fully implemented in `NextAppointmentCard.tsx` (fetch → find soonest upcoming ACTIVE booking → render nothing if none) — only its visual style changed, matching the reference's bold teal strip. (2) One real gap, the same class as the "Forgot password?" gap: `PatientAccount` (`backend/.../domain/PatientAccount.java`) has no name field at all — only email, password hash, mobile, notification opt-ins; there is no "the patient's name" concept anywhere at the account level (names only exist on per-clinic `Patient` records, which may differ or not exist yet). Adding a real name field is a schema change (migration + signup field + backfill decision), not a restyle. Resolved the same way as the password-reset gap: honestly derive a first-name-like display string from the authenticated email's local part (`deriveDisplayNameFromEmail`, e.g. "priya.sharma@example.com" → "Priya Sharma") rather than fabricating a name or leaving the greeting generic — consistent with this codebase's own pre-existing convention of falling back to email when no name exists (`LoginForm.tsx`'s post-login state already did this). A real "display name" account field, if wanted, is a separate, new backlog feature.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Fix confirmed layout/placement problems on shipped screens (Priority: P1)

As the product owner, after confirming with Claude exactly which shipped screen(s) from the 046-052 redesign have wasted space or irrational placement of the sidebar/fields/forms, I want those specific problems corrected so the product looks deliberate and polished rather than sloppy.

**Why this priority**: Layout/placement was the first and more visually obvious complaint raised, and fixing it is foundational — copy fixes on a page that still looks disorganized would not resolve the "looks sloppy" perception on their own.

**Independent Test**: Can be fully tested by opening any screen under the staff console's shared shell before and after the fix and visually confirming the sidebar is docked to the viewport edge with no nested centered columns, while `PatientShell`/`AdminShell` screens stay pixel-identical.

**Acceptance Scenarios**:

1. **Given** `StaffShell.tsx`/`ClinicShell.tsx`'s nested-centering structure (confirmed root cause: outer `max-w-5xl` centering plus a `flex`-nested sidebar plus per-form inner max-widths), **When** the fix is applied using the `orbit-1.0.0.zip` reference's edge-docked, sticky sidebar/full-width-content structure, **Then** every screen inheriting `StaffShell`/`ClinicShell` (not only `ClinicToolsDashboard.tsx`/`OnboardStaffForm.tsx`) shows the sidebar docked to the viewport's left edge (staying in view via `sticky` positioning as the page scrolls, not literally spanning full viewport height above the existing header) with content filling the remaining width, using CMS2's existing color tokens (no Orbit visual skin).
2. **Given** `PatientShell`/`AdminShell` and the screens under them were not named as having a layout problem, **When** this feature ships, **Then** those shells and screens are left visually unchanged.

---

### User Story 2 - Rebuild the landing page around real patient content and one clinic entry point (Priority: P2)

*(Expanded 2026-09-16, mid-implementation — see Clarifications: the product owner moved from "fix six pieces of generic copy on HomePage" to "rebuild HomePage from a prepared reference design," a materially larger but still explicitly confirmed scope.)*

As the product owner, having found `HomePage.tsx`'s copy generic/childish and its four-way role-picker layout unfocused, I want the page rebuilt around the patient booking flow (this system's primary audience) with concrete, specific copy, and clinic/admin access reduced to one quiet "Clinic login" link — matching a reference design I supplied, but with this project's own name, copy, routes, and design tokens.

**Why this priority**: Sequenced after layout (US1) because it was raised first, but independent of it — this page (`HomePage.tsx`) is outside `StaffShell`/`ClinicShell`'s scope entirely.

**Independent Test**: Load `/` and confirm: the hero is patient-booking content with working links to `/patient/login`, `/patient/signup`, and `/discover`; exactly one "Clinic login" link exists (header + footer), pointing at `/staff/login`; no top-level link to `/register` or `/super-admin-console` exists; `/staff/login` itself now offers a path to `/register`.

**Acceptance Scenarios**:

1. **Given** the reference design's layout/hierarchy (`design/landing-page-reference.html`), **When** `HomePage.tsx` is rebuilt, **Then** patient-booking content dominates the hero, using this project's brand name, copy, and `index.css` design tokens — not the reference's placeholder brand, palette, or font.
2. **Given** the reference's placeholder anchors (`#login`, `#signup`, `#clinic-login`, `#search`), **When** the page is wired up, **Then** each points at the corresponding real route (`/patient/login`, `/patient/signup`, `/staff/login`, `/discover`).
3. **Given** Super Admin auth and clinic registration must not be top-level homepage links, **When** the page ships, **Then** the only clinic-side link on `HomePage.tsx` is "Clinic login" → `/staff/login` (header and footer), and `/staff/login` itself offers a "Register your clinic" link to the existing `/register` route.
4. **Given** a heading/subheading on any screen other than `HomePage.tsx` was not named as a problem, **When** this feature ships, **Then** that copy is left unchanged.

### Edge Cases

- What happens if, during discussion, the product owner names a screen that does not exist or was never part of the 046-052 wave? → Surface this discrepancy back to the product owner rather than guessing at a substitute screen.
- What happens if a named layout problem's only real fix would require new functionality (e.g. adding content to fill empty space) rather than a spacing/placement adjustment? → Out of scope per this feature's own Business Rules (see `backlog/053-visual-design-copy-quality-pass.md`); flag it back to the product owner instead of building new functionality.
- How is a copy fix handled if the current text is asserted verbatim in an existing automated frontend test? → The confirmed, deliberate copy change takes precedence; the test is updated to match the new copy, not the reverse.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The discussion/clarification stage MUST identify, by name, every specific screen the product owner considers to have a layout/placement problem, before any layout change is made to that screen.
- **FR-002**: The discussion/clarification stage MUST identify, by quoted or clearly paraphrased text, every specific heading/subheading the product owner considers generic or overly simplistic, before any copy change is made for that text.
- **FR-003**: For each confirmed layout problem, the fix MUST be a targeted spacing/placement correction limited to the named issue on that screen — not a broader redesign of that screen or of any screen not named.
- **FR-004**: For each confirmed copy problem, the replacement text MUST describe that screen's actual purpose or the specific action a user takes there, and MUST NOT be a generic relabeling (swapping one vague word for another equally vague one).
- **FR-005**: Replacement copy MUST be consistent with the tone and terminology already documented in `PRODUCT.md` and the visual conventions already documented in `DESIGN.md`.
- **FR-006**: This feature MUST NOT introduce new functionality, new routes, new fields, or new user-facing capabilities beyond what is explicitly confirmed — only layout/spacing/placement and copy changes to already-shipped screens, **except** the `HomePage.tsx` rebuild and its routing consolidation explicitly directed by the product owner (see Clarifications, 2026-09-16 continued): removing the homepage's separate `/register` and Super Admin links (no new route — both destinations already existed) and adding a "Register your clinic" link to the existing `/staff/login` page (no new route — `/register` already existed). No backend endpoint, no new frontend route, and no new entity are introduced anywhere in this feature.
- **FR-007**: Any screen or text outside this feature's confirmed scope — `PatientShell`/`AdminShell` and any screen under them, plus any text on any screen other than the six confirmed elements on `HomePage.tsx` (FR-009) — MUST remain visually and textually unchanged. This is distinct from the many `StaffShell`/`ClinicShell`-inherited screens whose layout changes as an intended, confirmed consequence of the FR-008 structural fix (Clarifications, Q3) — that cascade *is* the confirmed scope, not an exception to this rule.
- **FR-008**: The layout fix MUST replace the nested-centering structure in `StaffShell.tsx` and `ClinicShell.tsx` (outer `max-w-5xl` centering wrapping a `flex`-nested sidebar) with an edge-docked, sticky, full-width sidebar/content structure — the pattern confirmed via the `orbit-1.0.0.zip` reference's `Layout.tsx`/`Sidebar.tsx`, adapted to `sticky` (not a literal viewport-edge-to-edge `fixed`/full-height element) so it doesn't collide with `StaffShell`'s existing header (research.md Decision 1) — applied once at the shared-shell level so every screen that inherits `StaffShell`/`ClinicShell` is corrected, not just `ClinicToolsDashboard.tsx`/`OnboardStaffForm.tsx`. `PatientShell`/`AdminShell` and their screens are out of scope for this pass.
- **FR-008a**: The layout fix MUST reuse CMS2's existing indigo/gray/cobalt color tokens and `PRODUCT.md`'s restrained tone — it MUST NOT introduce Orbit's own dark/glow visual skin or its animation library; only the structural sidebar/content mechanics are adopted.
- **FR-009**: *(Superseded — see FR-009a)* The copy fix MUST replace the following confirmed text on `frontend/src/routes/HomePage.tsx` with wording specific to what each element actually does, per FR-004/FR-005: the `<h1>` "One account, every clinic."; the intro subheading "Book appointments as a patient, run day-to-day operations as clinic staff, or manage verification as a Super Admin."; the "Patients" card body "Book appointments, join queues and waitlists, and manage your visits."; the "Clinic staff" card body "Manage schedules, bookings, walk-ins, and the day-to-day of your clinic."; the "Running a clinic?" card's "Register your clinic and admin account."; and the "Super Admin? Open the admin console" line.
- **FR-009a**: `HomePage.tsx` MUST be rebuilt to match the layout, spacing, and visual hierarchy of the product-owner-supplied reference (`design/landing-page-reference.html`): patient-booking content dominates the hero (headline, subheading, "Log in"/"Create account" actions, a low-emphasis link to `/discover`); a decorative illustration MAY accompany it on wide viewports; a "trust"/feature row names concrete, already-shipped capabilities. Brand name, copy, colors, and font MUST be this project's own (`CMS2 Clinic Management`, `index.css`'s existing indigo/gray/cobalt tokens, Figtree) — not the reference's placeholder brand ("Carepoint"), palette, or serif display font. All of the reference's placeholder anchors (`#login`, `#signup`, `#clinic-login`, `#search`) MUST be wired to this project's real routes (`/patient/login`, `/patient/signup`, `/staff/login`, `/discover`).
- **FR-010**: `HomePage.tsx` MUST expose exactly one clinic-side entry point — a single, low-emphasis "Clinic login" link, present in both the header and the footer, pointing at the existing `/staff/login` route. No other clinic- or admin-facing link (registration, Super Admin) MAY appear at the top level of this page.
- **FR-011**: Super Admin authentication and clinic registration MUST both be reachable only from behind the single "Clinic login" entry point (FR-010), not as separate top-level links on `HomePage.tsx`: Super Admin sign-in already role-routes correctly from the existing `/staff/login` form (`decideClinicPortalDestination`, no change required); a link to the existing `/register` route MUST be added to the `/staff/login` page itself so clinic registration remains reachable.
- **FR-012**: `/patient/login` (`PatientLoginPage.tsx`/`LoginForm.tsx`) MUST be rebuilt to match the layout, spacing, typography, and copy structure of `design/patient-login-reference.html`: the same branded header/footer as `HomePage.tsx` (FR-010's `BrandHeader`/`BrandFooter`), a centered card with a "Welcome back." heading, email + password fields with proper label association, a "Forgot password?" affordance inline with the Password label, a full-width primary submit button, and a quiet divider + "Create an account" line below. It MUST reuse this project's own tokens (not the reference's palette/font) and wire every placeholder anchor to the real flow: email/password submit through the existing `loginPatient` API call, "Create an account" → `/patient/signup`, "Clinic login" → `/staff/login`. Since no password-reset capability exists anywhere in this system, "Forgot password?" MUST NOT link to a fabricated flow or a dead anchor — it surfaces an honest in-app notice instead (FR-006's "no new functionality" boundary applies here: a real reset flow is out of scope for this rebuild).
- **FR-013**: `/patient` (`PatientDashboard.tsx`/`PatientShell.tsx`) MUST be rebuilt to match `design/patient-dashboard-reference.html`: a branded header (this project's own brand mark/wordmark, matching the login/landing pages) with an account menu (avatar, email, sign-out) instead of a "Clinic login" link; a personalized "Welcome back, {name}." heading; a highlighted "next visit" strip; and three action cards (Find a doctor, My bookings, My clinics) with icon, title, arrow, and description. The next-visit strip MUST render only when the signed-in patient has a real upcoming booking (reusing `NextAppointmentCard.tsx`'s existing fetch/find-soonest-upcoming/render-nothing-if-none logic, restyled only, not reimplemented) — never an empty or placeholder strip. Sign-out and the three action cards MUST use real routes/logic (unchanged `signOut`/`loginPatient`-adjacent behavior; `/discover`, `/patient/bookings`, `/patient/clinics`). Since `PatientAccount` has no name field anywhere in this system, the greeting and avatar initial MUST use a name derived from the authenticated email (`deriveDisplayNameFromEmail`), not a fabricated name — a real name field is out of scope for this rebuild (FR-006).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of screens under the confirmed `StaffShell`/`ClinicShell` structural scope show the corrected layout, with zero visual change to `PatientShell`/`AdminShell` or any screen under them — the only scope explicitly excluded during discussion.
- **SC-002**: `HomePage.tsx` matches the reference design's layout/hierarchy using this project's own brand/copy/tokens, with 100% of the reference's placeholder anchors wired to real routes, and exactly one clinic-side link (Clinic login) at the top level.
- **SC-003**: When the product owner reviews the fixed screens after this feature ships, they confirm in conversation that the specific problems they raised are resolved, with no new complaint that changes were guessed at or unrequested.
